# 力扣 12 题：整数转罗马数字 (Integer to Roman)

## 一、 挑战点与思路梳理

### 挑战点
1. **特殊规则处理**：罗马数字除了标准的叠加，还包含 6 种特殊的减法规则（如 4 对应 IV，9 对应 IX），必须在转换时妥善处理。
2. **降序匹配逻辑**：转换原则是优先使用“最大符号”。如何设计合适的数据结构，确保匹配过程严格按照从大到小的顺序进行。
3. **边界条件利用**：题目设定数值范围为 1 到 3999，这意味着每位上的字符组合是有限且固定的，可以利用这一硬性边界大幅度简化代码逻辑。

### 思路概述
* **贪心算法**：将所有符号（包含特殊减法组合）按对应数值降序排列，只要当前数字大于等于某个符号的值，就不断扣减并拼接该符号。
* **查表法（硬编码）**：由于输入范围固定且每位互不干扰，预先写死千位、百位、十位、个位的所有罗马数字可能。通过整除和取余提取每位数字，直接按索引查表拼接。

## 二、 核心疑问与专项代码解答

### 1. 贪心算法是如何做到向下查找并扣减的？
贪心算法的核心在于维护一个**严格降序**的映射结构，并通过循环不断扣减。
```python
# 核心映射表与扣减逻辑
value_symbols = [
    (1000, "M"), (900, "CM"), (500, "D"), (400, "CD"),
    (100, "C"), (90, "XC"), (50, "L"), (40, "XL"),
    (10, "X"), (9, "IX"), (5, "V"), (4, "IV"), (1, "I")
]
roman_digits = []
for value, symbol in value_symbols:
    while num >= value:      # 只要当前数字够大
        roman_digits.append(symbol) # 拼接对应符号
        num -= value         # 扣减对应数值
```

### 2. 边界条件（1-3999）如何简化代码？
在这个固定范围内，我们可以完全消灭循环和比较判断，转化为对四个有限数组的索引寻址（查表法）。
```python
# 将数字的每一位剥离，直接作为数组的索引
# 假设 num = 1994
thousands[num // 1000]            # 千位: 1994 // 1000 = 1 -> "M"
hundreds[(num % 1000) // 100]     # 百位: 994 // 100 = 9 -> "CM"
tens[(num % 100) // 10]           # 十位: 94 // 10 = 9 -> "XC"
ones[num % 10]                    # 个位: 4 -> "IV"
```

### 3. 如何在查表法的基础上做到极致的执行效率？
可以利用底层特性进行微调优化：将可变的列表 `[]` 替换为不可变的元组 `()` 以优化内存，并将字符串相加 `+` 替换为底层的 `f-string` 插值以加快拼接速度。

## 三、 完整代码实现（极致优化打表法）

针对 Python 环境与 LeetCode 的运行机制，这是目前效率极高（击败率极高）的解法。采用类属性避免重复分配内存，采用元组与 f-string 压榨时间开销。

```python
class Solution:
    # 静态数据区：将映射表设为类属性，并使用不可变的元组 () 提升寻址效率
    THOUSANDS = ("", "M", "MM", "MMM")
    HUNDREDS  = ("", "C", "CC", "CCC", "CD", "D", "DC", "DCC", "DCCC", "CM")
    TENS      = ("", "X", "XX", "XXX", "XL", "L", "LX", "LXX", "LXXX", "XC")
    ONES      = ("", "I", "II", "III", "IV", "V", "VI", "VII", "VIII", "IX")

    def intToRoman(self, num: int) -> str:
        # 核心逻辑：利用数学运算剥离每一位，直接查表
        # 使用 f-string 进行字符串拼接，比使用 + 号在底层内存分配上更高效
        return f"{self.THOUSANDS[num // 1000]}{self.HUNDREDS[(num % 1000) // 100]}{self.TENS[(num % 100) // 10]}{self.ONES[num % 10]}"
```

## 四、 复杂度与总结

* **时间复杂度**：$O(1)$
  无论输入的数据是 1 还是 3999，代码都只执行固定次数的整除、取余和数组索引访问。计算步骤不随数据规模变化而增加，属于严格的常数时间复杂度。
* **空间复杂度**：$O(1)$
  创建了四个总计几十个元素的映射表（或元组），占用的内存是极小的常数级别。返回结果所占用的字符串空间通常不计入辅助空间复杂度，因此空间消耗为 $O(1)$。

**总结**：在实际工程或竞赛中，如果遇到输入范围被严格限制（如本题的 3999 上限）的场景，优先考虑“空间换时间”的查表法。它不仅能将时间复杂度降到最低，还能大幅度减少代码逻辑层面的 Bug 率。
